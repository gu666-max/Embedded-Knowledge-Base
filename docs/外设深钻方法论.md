<a id="why"></a>

## 一、为什么改

### 1. 旧路径 vs 新路径

| | 旧路径（广度优先） | 新路径（深度优先） |
|---|---|---|
| 目标 | 外设**数量** | 少数外设的**深度** |
| 产物 | 一个能跑的 Demo | 一个可复用资产包 |
| 面试表现 | 每个外设都能说两句 | 有两三个能被追问 5 层以上 |
| 时间感 | 一直在学新东西 | 大量时间在和同一个东西较劲 |
| 遇到新项目 | 从零再查一遍 | 打开资产包，半天接进去 |

### 2. 三句结论

1. **广度决定你能不能上手，深度决定别人要不要你。**
2. **项目里的模块大多是别人写好的；你能"深"的，只有自己啃过的那几个。**
3. **深度只有在能被复用时才算资产，否则只是经历。**

### 3. 新的默认动作

- 每接触一个外设，先问一句：**它会不会出现在我后面 80% 的项目里？**
- 会 → 进 `peripherals/`，按 18 天时间盒做到 L6，沉淀成资产包。
- 不会 → 只做到 L3，留一页笔记，标记为「样本」，不进资产库。
- **不背代码。** 第一次写出来、理解原理、记下结论，之后查自己的笔记或手册即可。

> 嵌入式不是考试。考试要求你从空白页复现；工作要求你**知道该查什么、查到能判断对错**。

<a id="illusion"></a>

## 二、三个必须先拆掉的错觉

| 错觉 | 表现 | 真相 |
|---|---|---|
| **深入 = 把 Reference Manual 读完** | 翻了 300 页，配置还是抄的 | 深度是「能回答具体问题」，不是「读过多少页」。读完但说不出一个配置位为什么取这个值 = 0 深度 |
| **深入 = 会写驱动** | 能收发数据就认为学完了 | 那只到第 3 层，一共 6 层。只到 L3 的人，系统一集成必然翻车 |
| **深入 = 背下来** | 纠结自己记不住寄存器名 | 记忆不是资产，**可检索的结论**才是。你要练的是"知道去哪查、查完能判断" |

**判定标准只有一条：能不能在没人提示的情况下，把一个具体问题讲穿。** 讲不穿就是没懂。

<a id="six-layers"></a>

## 三、六层深入模型

```
        ┌──────────────────────────────────────────┐
   L6   │ 验证与实测   波形 / 极限 / 故障注入        │  ← 面试弹药
        ├──────────────────────────────────────────┤
   L5   │ 系统集成     资源冲突 / 抖动 / 功耗 / 互扰  │  ← 拉开差距
        ├──────────────────────────────────────────┤
   L4   │ 抽象与移植   core / port 分离              │  ← 能复用
        ├──────────────────────────────────────────┤
   L3   │ 驱动设计     状态机 / 异常恢复 / ISR 安全   │  ← 能干活
        ├──────────────────────────────────────────┤
   L2   │ 寄存器机制   为什么是这个值，改错会怎样     │  ← 真懂
        ├──────────────────────────────────────────┤
   L1   │ 电气物理     时序 / 容限 / 极限参数         │  ← 地基
        └──────────────────────────────────────────┘
```

### L1 电气与物理层

| 项 | 内容 |
|---|---|
| 核心问题 | 这个信号在物理上是什么样？能拉多远、多快、带多重？ |
| 动作 | 读芯片 datasheet 电气特性表与时序图；用示波器/逻辑分析仪实测波形；算上升沿、建立/保持时间、驱动电流、负载电容 |
| 过关标志 | 能画出关键信号时序图并标出容限；能解释一个"接上能跑但偶发失败"的物理原因 |
| 失败信号 | 只会说"按参考设计接的，能跑" |

### L2 寄存器与硬件机制

| 项 | 内容 |
|---|---|
| 核心问题 | 为什么这样配？改一个位会怎样？ |
| 动作 | 逐位标注配置来源（手册章节号）；做**改一个位的破坏实验**，记录现象 |
| 过关标志 | 任取一个配置位，能说出作用 + 填错后的现象 + 为什么会这样 |
| 失败信号 | 配置是复制来的，不敢改、也不知道改了会坏成什么样 |

### L3 驱动设计

| 项 | 内容 |
|---|---|
| 核心问题 | 正常路径之外，异常怎么收场？ |
| 动作 | 画完整状态机；列出 ≥5 条异常路径（超时/无应答/忙/溢出/掉线/CRC 错）；做重入与 ISR 安全分析 |
| 过关标志 | 每种异常都有「检测 → 恢复 → 上报」三件套；拔线、断电、乱序都能自己活过来 |
| 失败信号 | 驱动只有 happy path；出错就死等或重启 |

### L4 抽象与移植

| 项 | 内容 |
|---|---|
| 核心问题 | 换一颗 MCU，要改多少行？ |
| 动作 | core（协议/时序逻辑，平台无关）+ port（寄存器/延时/中断，平台相关）分离；port 层函数 ≤ 8 个 |
| 过关标志 | 换芯片只改 port 层，core 一行不动 |
| 失败信号 | 驱动里直接出现寄存器名、`HAL_`、`GPIOA` |

### L5 系统集成

| 项 | 内容 |
|---|---|
| 核心问题 | 在系统里被谁挤？挤坏了长什么样？ |
| 动作 | 填资源占用表（DMA 流 / 定时器 / 中断优先级 / 栈 / Flash / RAM / 功耗）；测最坏延迟与抖动；做互扰实验（PWM 与 ADC 同时开、通信与 Flash 写入同时进行） |
| 过关标志 | 能说出最坏情况下对本系统的影响，以及保底手段（降级/重试/看门狗/隔离） |
| 失败信号 | 单独跑没问题，一上系统就偶发 |

### L6 验证与实测

| 项 | 内容 |
|---|---|
| 核心问题 | 你怎么知道它是对的？怎么知道它在边界上还是对的？ |
| 动作 | 留波形证据；测极限值（最高速率、最低电压、最差温度、最大负载）；做故障注入；记录优化前后的对比数字 |
| 过关标志 | 有可复现的测试台 + 具体数字 + 波形文件 |
| 失败信号 | 结论只有一句"测试通过" |

<a id="verify"></a>

## 四、验收法：讲得清楚才算过

面试不会问"你学过 DMA 吗"，它会顺着你的话往下钻。把这条追问链当自测题：

| 层 | 追问 | 合格回答必须包含 |
|---|---|---|
| 1 | 你是怎么做的？ | 步骤 + 关键参数（不是"用了 DMA"） |
| 2 | 为什么这么选？ | 备选方案 + 淘汰理由（"为什么不是中断/轮询"） |
| 3 | 边界在哪？ | 极限条件 + 还剩多少余量 |
| 4 | 怎么验证的？ | 方法 + 数据 + 波形（不是"能跑"） |
| 5 | 坏了怎么办？ | 检测手段 + 恢复流程 + 上报方式 |

### 自测动作（每个外设必做一次）

1. 不看笔记，对着手机录音讲 3 分钟。
2. 回放，标出卡住的层号。
3. 卡在哪层，就回去补哪层——**不要重读整本手册**。
4. 录音留在 `evidence/`，文件名带日期。

> 这条比"写出来"更严格：写代码可以查、可以试错；讲，是把你脑子里的模型直接倒出来。

<a id="choose"></a>

## 五、选哪个外设去钻

### 三条判据（同时满足才值得投 2~3 周）

1. **复用率**：几乎每个项目都会用到。
2. **失败模式多**：坑多、非直观，深度真能拉开差距。
3. **面试密度高**：能被追问 5 层以上。

### 第一梯队（先做 3 个）

| 外设 | 值得钻的角度 | 典型坑 |
|---|---|---|
| **DMA** | 外设↔内存全链路数据通路 | Cache 一致性、双缓冲语义、传输完成/半完成中断时序、与 CPU 访问竞争 |
| **定时器** | 全系统时间基准的统一 | 预分频与 ARR 的生效时机、捕获溢出回绕、PWM 死区与互补、编码器模式 |
| **ADC** | 从模拟前端到数字值的完整链路 | 采样时间与源阻抗、参考电压与校准、多通道扫描 + DMA、噪声与滤波 |
| **UART + DMA + IDLE** | 通信可靠性与帧同步 | 空闲中断判帧、半包/粘包、ORE 清除顺序（先读 SR 再读 DR）、波特率误差累积 |

### 第二梯队（有余力再做）

SPI（时序模式、片选、DMA 收发）｜I2C（时钟拉伸、总线死锁与恢复、仲裁）｜Flash/EEPROM（磨损均衡、掉电原子性）｜低功耗（唤醒源、RTC、实测电流）｜看门狗（复位原因判定、恢复流程）

### 样本类（学到 L3 即可）

DHT11 / 单总线 —— 复用率低，但"时序方法论 + 末位无下降沿容错"是绝佳教材。**这类东西的价值是方法，不是代码。**

## 六、时间盒：18 天一个外设

每天按 2~3 小时算。时间盒的作用不是赶进度，是**防止"深入"变成逃避动手的借口**。

| 天 | 阶段 | 交付物 |
|---|---|---|
| D1–D2 | L1 电气与手册 | 时序图 + 配置表初稿（每项带章节号） |
| D3–D5 | L2+L3 最小驱动 | 能收发的最小代码 + 第一张波形 |
| D6–D8 | L3 驱动完善 | 状态机 + ≥5 条异常路径 + 自检函数 |
| D9–D11 | L4 抽象 | core/port 分离，换板验证 |
| D12–D14 | L5 集成 | 资源占用表 + 延迟/抖动数据 + 互扰实验 |
| D15–D16 | L6 验证 | 故障注入记录 + 极限值 + 优化前后对比 |
| D17–D18 | 沉淀 | README + 笔记 + evidence，录 3 分钟讲解 |

**超时规矩**：到点没做完就停手，把没解决的问题写进 `notes/未解问题.md`，转入下一个外设。
回来补是允许的，但**不允许无限期停在一个外设上**——那叫拖延，不叫深入。

## 七、资产包结构

位置：`peripherals/<外设名>/`

```
peripherals/dma/
├─ README.md          ← 唯一入口。结论先行，别人（和半年后的你）只读这个就能用
├─ notes/             ← 原理、寄存器、推导过程、未解问题
├─ driver/            ← core（平台无关）+ port（平台相关）
├─ test/              ← 自检、压测、故障注入，能一键复现结论
└─ evidence/          ← 波形、实测数据、对比表、讲解录音
```

### 命名规范

- 目录：小写 + 下划线，用外设通用名（`dma`、`tim1_pwm`、`adc_scan`）
- core 文件：`<name>_core.c/.h`；port 文件：`<name>_port.h`、`<name>_port_stm32f4.c`
- 测试：`test_<name>.c`
- 证据：`<日期>_<内容>.md/.png/.csv`，例：`2026-11-12_dma_htx_latency.png`

### 准入条件（缺一条就不算沉淀完成）

- [ ] `README.md` 能独立支撑"别人接进去"
- [ ] `driver/` 中 core 层无任何平台相关内容
- [ ] `test/` 能在 1 条命令内跑出结论
- [ ] `evidence/` 至少有一个波形 + 一组数字 + 一次故障注入
- [ ] 有 3 分钟讲解录音，且五层追问链没有卡壳

## 八、笔记怎么写才"查得到"

一年后的你不认识现在的你。笔记的唯一目标是：**打开就能用，不用重新推导。**

| 要素 | 要求 | 无效写法 | 有效写法 |
|---|---|---|---|
| 结论 | 每节第一句就是结论 | "DMA 配置比较重要" | "DMA 必须双缓冲，否则半包丢失率 >3%（实测）" |
| 参数 | 带取值理由与反例 | "NDTR 设为 sizeof(buf)" | "NDTR = 256：受 SRAM 突发长度限制；设 512 时两次传输间出现 12µs 空窗" |
| 引用 | 带手册章节号 | "见参考手册" | "RM0090 §30.3.4" |
| 坑 | 现象 → 根因 → 修法 | "这里有问题，已解决" | "现象：偶发丢首字节；根因：ORE 未按 SR→DR 顺序清除；修法：先读 SR 再读 DR" |
| 未解 | 单独成节，明确标注 | 假装全懂 | "【未验证】高温下时序是否仍满足，待复测" |

**规矩：任何没有数据支撑的结论，必须标注【未验证】。** 这是对未来的自己诚实。

<a id="antipattern"></a>

## 九、反模式清单

1. **只读手册不动手** —— 读完 300 页，一个位也说不出所以然
2. **抄配置不敢改** —— 没做过破坏实验，等于没学过
3. **只有 happy path** —— 没有超时、没有重试、没有错误上报
4. **在中断里做业务** —— 一次能跑，量产必翻车
5. **用 delay 代替状态机** —— 阻塞式思维，永远做不了多任务
6. **没有时间盒** —— 深钻变成无限期停摆
7. **笔记写成手册摘抄** —— 复制了 200 行寄存器表，没一句自己的判断
8. **只测正常情况** —— 没有边界、没有极限、没有故障注入
9. **为一个外设造框架** —— 抽象过度，复用率反而下降
10. **深了但不记录** —— 下次从零开始，等于白钻

<a id="checklist"></a>

## 十一、一页检查清单

复制到每个外设的 `README.md` 末尾，逐项打勾。

**L1 电气**
- [ ] 有时序图，标注了容限
- [ ] 能解释一个偶发失败的物理原因

**L2 寄存器**
- [ ] 每个配置项都写了"为什么是这个值"
- [ ] 做过至少 3 次"改一个位"的破坏实验

**L3 驱动**
- [ ] 有完整状态机图
- [ ] ≥5 条异常路径，每条都有检测/恢复/上报
- [ ] 通过重入与 ISR 安全审查

**L4 抽象**
- [ ] core 层无平台相关代码
- [ ] 换板/换芯片只改 port 层（实际验证过）

**L5 集成**
- [ ] 资源占用表（DMA/定时器/中断优先级/栈/RAM/Flash）
- [ ] 最坏延迟与抖动的实测数字
- [ ] 至少一次互扰实验

**L6 验证**
- [ ] 波形证据（文件在 evidence/）
- [ ] 极限值测试记录
- [ ] 故障注入 ≥8 项
- [ ] 优化前后对比数据

**沉淀**
- [ ] README 能让别人直接接入
- [ ] 笔记有结论、有章节号、有【未验证】标注
- [ ] 3 分钟讲解录音，五层追问不卡壳

## 现在开始

1. 从第一梯队里挑一个（建议 **DMA** 或 **UART + DMA + IDLE**，坑最多、复用最高）。
2. 复制 `peripherals/_模板/` 为 `peripherals/<外设名>/`。
3. 在仓库根 `README.md` 的进度表里登记，写上开始日期与目标完成日。
4. D1 只做一件事：**把时序图画出来**。画不出来，说明还没开始。
